# DulceCalle — M6.0 / M6.1 / M6.2 / M6.3 / M6.4

Offline-first comes later. This document is the contract for the local
foundation. **Do not treat it as a live sync engine.**

The PWA UI still talks HTTP (`pwaStorage() === "http"`). Pages must not
dual-write. Legacy Dexie `"dulcecalle"` (`++id`) stays for domain tests and
the palette. `import_id_map` stays import-only.

---

## M6.0 — decisions

### UUID local

New M6 entities use a client-minted UUID as PK (`newEntityId()` /
`crypto.randomUUID()`). Same value is the identifier PostgreSQL should
eventually persist. There is **no** `381 → UUID` map for M6 ops.

`import_id_map` is not used for live sync.

Local customer `code` is `null` until the server assigns `DC-NNNN`.
Never invent `DC-TEMP` / `DC-PENDING` / `DC-9999`.

### requestId

`newRequestId()` returns a UUID or throws. No `prefix-Date.now-random`
fallback (the API rejects that as `Idempotency-Key`).

- `operationId` = outbox row identity
- `requestId` = HTTP intent / Idempotency-Key
- They are different fields. A retry **reuses** the stored `requestId`.

### Customer / supplier create

`POST /v1/customers` and `POST /v1/suppliers` require `Idempotency-Key`
(same pattern as products). Same key → same row, same server `code`.
The client does not compute `DC-NNNN`.

### Auth / network

`HttpClient`: `Failed to fetch` / timeout / abort → `NetworkError`,
**session kept**. Refresh `401`/`403` → `session.clear()` (invalid token).
Refresh `5xx` → session kept.

No passwords in Dexie. M6.2: session continuity on NetworkError (below).

## M6.1 — Local Store + Outbox

Database name: **`dulcecalle-local`**. Separate from legacy `"dulcecalle"`.
No automatic number→UUID migration.

Every business row and every outbox row has `businessId`. Reads filter by
it; `get(id)` of another tenant returns `undefined`.

Tables: products, customers, suppliers, sales, saleLines, saleReturns,
saleReturnLines, stockMoves, cashSessions, cashMoves, expenses,
customerPayments, initialDebts, outbox.

`stock`, `debt`, `avgCost`, `expectedEfectivo`, `expectedNequi` on the
local rows are **CACHE / OPTIMISTIC**. PostgreSQL is the authority.

Outbox fields: `operationId`, `businessId`, `entity`, `operation`,
`requestId`, `payload`, `dependsOn[]`, `localCreatedAt`, `status`
(`pending` | `in_flight` | `synced` | `failed`), `remoteId`, `attempts`,
`lastError`, `nextAttemptAt`. FIFO via `localCreatedAt`. Unique
`(businessId, requestId)`. Retry of the same `operationId` must send the
same `requestId`. `put` refuses to move an id to another `businessId`.

Code: [`src/data/local/`](src/data/local/). Catalog **read** cache is
wired through stores (`listCached*`). Outbox still has no flush. No
Sync Engine, no Background Sync.

## M6.2 — Auth offline (session continuity)

First login is **online-only**. No password, hash, or reusable credential
is stored — only the tokens + user/customer profile + (admin) `businessId`
already in `dulcecalle.auth` / `dulcecalle.customer.auth`.

`HttpSession.authenticated` / `CustomerSession.authenticated` follows the
**refresh** token. If refresh is a JWT with numeric `exp` already in the
past, the session is not authenticated locally — AuthGate goes to login
even offline. Access `exp` (15m) is ignored by the gate so a live refresh
(7d) still survives an expired access after a PWA restart. Non-JWT
strings (no `exp`) keep the previous presence rule. AuthGate
(`decideAuthGate`) reads that local state and **does not fetch**. Empty
storage stays on `/login` (or `/cliente/login`). An admin session never
opens the customer portal and vice versa. One admin session holds one
`businessId`.

Refresh behaviour stays in [`HttpClient`](src/data/http/client.ts) (M6.0):

- `NetworkError` / refresh `5xx` → session **kept**, operation fails as red
- refresh `401` / `403` → `session.clear()`, back to login
- refresh online still rotates tokens

Not in M6.2: Sync Engine, outbox flush, offline writes, `/sync`.

## M6.3 — Read cache (catalog)

HTTP GET of the admin catalog is stored in `dulcecalle-local` as a
**read copy**. PostgreSQL remains the authority. No writes, no outbox
flush, no `/sync`.

### Strategy

- **Online:** GET backend → valid response (including `[]`) → replace
  the tenant snapshot → return server data (`source: "server"`).
- **NetworkError:** if `cacheMeta` exists for that tenant+resource →
  return the snapshot (`source: "cache"`). If it does not exist →
  **rethrow**. Never invent rows. Never hide a miss as `[]`.
- **401 / 403:** rethrow. Do **not** serve cache (auth is invalid).
- **5xx:** rethrow. The server answered; it is still the authority.
  Stale catalog is not substituted for an explicit server failure.

### Resources (admin panel)

| Resource | Endpoint | Table | Id | Tenant |
|---|---|---|---|---|
| Products | `GET /products` | `products` | UUID | `businessId` |
| Customers | `GET /customers` | `customers` | UUID | `businessId` |
| Suppliers | `GET /suppliers` | `suppliers` | UUID | `businessId` |

`updatedAt` on each row is the **cache write time**. Dexie **v2** adds
`cacheMeta` (`id = businessId::resource`, `cachedAt`) so an empty GET
is distinct from “never cached”. Version 1 tables are unchanged.

Not cached in M6.3 (computed, dated, or N+1; writes still online):
`GET /cash/today`, sales, expenses, stats, ledger, stock moves,
surtidas, customer portal. Dashboard still needs those GETs online.

### Isolation

`LocalStore.list/get/replaceAll` stay tenant-scoped. Business B cannot
read A’s snapshot. Same id on another tenant is refused.

GET never enqueues Outbox.

## M6.4 — Connectivity + Outbox Flush

M6.4 adds the generic synchronization foundation without inventing business write payloads. The PWA still does not perform offline sales, payments, cash, inventory, expenses, customer creation, or supplier creation from the UI.

### Connectivity

ConnectivityMonitor listens to browser online/offline events and exposes a local hint. It does not perform a network probe and it does not log out the session. A later UI/bootstrap layer can subscribe and trigger a flush.

### Outbox flush

OutboxSyncEngine.flush(businessId, sender):

- recovers in_flight rows after a reload because HTTP operations are idempotent and reuse the stored requestId;
- processes pending and due failed rows in deterministic FIFO order;
- requires every dependsOn[] operation to be synced before sending;
- marks successful operations synced with a validated remoteId;
- retries network, 408, 429 and 5xx failures with exponential backoff, capped at five minutes;
- keeps requestId unchanged on every retry;
- marks permanent API errors as failed without deleting the operation;
- stops the current flush on connectivity failures or 401/403;
- keeps all outbox reads/writes tenant-scoped.

The engine receives an OutboxSender from the phase that owns each business operation. This is intentional: M6.4 does not guess endpoint payloads for M6.5+ and therefore cannot accidentally execute a business mutation that has not been designed and tested yet.

No /sync endpoint, Background Sync, UI offline-write mode, or business write operation is added by M6.4.

### Later (not this phase)

- M6.4 connectivity flush
- M6.5+ offline writes

## M6.5 — Offline sales

M6.5 enables sales while offline using the cached catalog. Online sales remain
server-authoritative; only a `NetworkError` falls back to the local store.

An offline sale atomically records the sale, sale lines, optimistic stock move,
cash move when money was received, customer debt increase when fiada, and one
outbox operation. The same `requestId` is reused when syncing so a lost HTTP
response cannot create a duplicate sale.

The connectivity bridge flushes sale operations automatically when the browser
returns online. Local financial values remain optimistic until PostgreSQL
accepts the operation.

## M6.6 — Offline customer payments

M6.6 enables customer debt payments (abonos) while offline using the cached
customer debt.

An offline payment atomically records the customer payment, optimistic debt
decrease, cash inflow, and one outbox operation. The same `requestId` is
reused for every retry.

The backend payment endpoint is idempotent and performs the authoritative
customer-debt decrement and cash movement in one transaction. It rejects an
abono that exceeds the current server debt.

Sale and payment flushes are filtered independently so one operation type
cannot mark another type as failed. Both are triggered by the existing PWA
sync bridge when connectivity returns.

Not in M6.6: offline customer creation, offline cash-session opening/closing,
conflict UX, or offline customer ledger snapshots.
